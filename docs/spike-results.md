# 预研结论：CodeMirror 6 大文件与中间工具条对齐

日期：2026-10-19  
环境：Headless Chrome 154 / Linux x86_64（本机没有 Mac，排版用的是 Chromium）  
原型：`spike/`（`pnpm spike` 可复现，原始数据在 `docs/spike-results.json`）  
结论：**继续用 CodeMirror 6，不换 Monaco。** 工具条色带误差为 0px；同步滚动在锁住回声并做一帧屏幕坐标修正后，滚动、折叠、字号、窗口高度、CSS zoom 1.25/1.5/2 的最大误差 **0.5px**，满足研发设计「不超过 1px」。

## 测了什么

左右各一份约 10 万行、6.2MB 的 JavaScript 文本（左 100001 行 / 6270398 字节，右 99713 行 / 6255488 字节），260 个不对称差异块（其中 23 个纯插入，左右行号会岔开）。每个场景在 16 个锚点上各测两次滚动偏移，共 32 个样本。语法高亮开、关各跑一遍。

场景：滚动、折叠未改动区域、字号 16px、字号 20px、把对比区高度收到 420px、CSS zoom 125% / 150% / 200%。

## 对齐误差（修正之后）

色带用左右行的 `getBoundingClientRect` 算，再除以一个 100px 探针对出的 CSS zoom。两种高亮设置下数字一样：

| 场景 | 色带最大误差 | 同步滚动最大误差 | 样本 |
| --- | ---: | ---: | ---: |
| 滚动 | 0 px | 0.5 px | 32 |
| 折叠 | 0 px | 0.5 px | 32 |
| 字号 16px | 0 px | 0.375 px | 32 |
| 字号 20px | 0 px | 0 px | 32 |
| 窗口变矮 | 0 px | 0 px | 32 |
| zoom 125% | 0 px | 0.5 px | 31–32 |
| zoom 150% | 0 px | 0.5 px | 32 |
| zoom 200% | 0 px | 0 px | 32 |

最大误差 **0.5px**。

## 不修正时会偏多少，以及原因

只做「按差异块锚点分段线性映射」时，折叠后最大偏 **56.4px**，第一次把字号从 13px 改成 16px 最大偏 **69.1px**（大约 3 行）。第二次再改到 20px 又是 0。原因有两个：

1. `EditorView.documentTop` 是屏幕坐标，不能拿来加 `scrollTop`。行块的 `lineBlock.top` 才和 `scrollTop` 同一套；CSS zoom 下还要再除以 `view.scaleY`（CM6 用 `getBoundingClientRect / offsetHeight` 得到）。
2. 折叠或改字号之后，CM6 会按自己的滚动锚点改 `scrollTop`，分段映射留下大约 3 行的残差。若这时去改另一栏的 `scrollTop`，对栏的 `scroll` 监听会立刻用旧映射把修正盖掉（回声）。

正式实现采用的做法（原型里已验证）：

- 同步期间加锁，两边的滚动监听直接返回。
- 先用锚点映射跳过去。
- 再读左右锚点行的屏幕 Y，把右栏 `scrollTop` 加上 `(右Y - 左Y) / scale`，最多再补一帧。
- 然后才解锁。
- 色带、按钮只使用 `getBoundingClientRect` 相对工具条容器的差值，不混用 `offsetTop`。

字号、折叠、缩放之后要等 `contentHeight` 连续两帧不变再重算锚点。

## 和 Monaco 的关系

这一档 CM6 能在 1px 以内对齐，也能扛住 10 万行。不再做 Monaco 对照原型。
